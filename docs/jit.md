# 机器码与 `[[jit]]`

`[[jit]]` 只表达一件事：**这个函数值得在加载时就优化**。它不改变语义——同一个函数带标记和不带
标记，结果（包括 `typeof`）必须完全一致，见 `examples/jit.ant`。

```annota
[[jit]]
sum_to(n)(
    new s = 0
    new i = 0
    while i < n(
        s = s + i
        i = i + 1
    )
    =s
)
```

**不写这个标记也照样优化**：热循环会被解释器自己编译成机器码（§1）。`[[jit]]` 只是把时机提前。

## 1. 自动优化（不需要任何标注）

解释器自己数循环：一个循环的回跳超过阈值（默认 4000 次，`ANNOTA_JIT_THRESHOLD` 可调）后，它会在
运行中把整个函数编译成机器码，并且**当场从当前循环头切过去执行**（on-stack replacement）——不必
等下一次调用，也不用重启程序。翻译不了就安静地继续解释执行。

所以：

| 写法 | 行为 |
| --- | --- |
| 什么都不写 | 热循环跑到阈值后自动编译并接管 |
| `[[jit]]` | 加载阶段就编译（适合"只调用一次、但循环很长"的函数） |
| `ANNOTA_JIT_THRESHOLD=0` | 关闭自动提升（`[[jit]]` 仍然生效） |
| `ANNOTA_NO_JIT=1` | 完全关闭机器码后端，只保留超指令融合 |
| `ANNOTA_JIT_DEBUG=1` | 打印哪个函数被自动编译、哪个不可翻译及原因 |

## 2. 超指令融合（所有函数都有）

融合保持字节码长度不变（空出来的位置填 `nop`），所以所有跳转目标仍然有效。 这些融合对**每个**
函数生效，不再只属于 `[[jit]]`（`[[jit]]` 在此基础上额外启用"比较并跳转"这一对，并立刻编译机器码）：

| 原序列 | 融合为 | 生效范围 |
| --- | --- | --- |
| `s = s + k` / `s -= k` | `local+=` / `local-=` | 所有函数 |
| `s = s + t` | `local+=local` | 所有函数 |
| `a[i][j]`（二维下标） | `get_index2` / `set_index2` | 所有函数 |
| `i < n` + 条件跳转 | `local<local?` | 仅 `[[jit]]` |
| `i < k` + 条件跳转 | `local<imm?` | 仅 `[[jit]]` |

`get_index2` 对数组直接按 stride 算元素，**不再生成中间的行视图**（行视图会复制整个 `Obj`），
越界检查与报错文本和两次下标完全一致。

想看自己代码融合成了什么：

```powershell
build\annota.exe check --dump-bc examples\jit.ant
```

调试时可以逐条开关融合（`bit0` 局部加立即数、`bit1` 比较并跳转、`bit2` 下标加立即数、`bit3` 局部加局部）：

```powershell
$env:ANNOTA_FUSE = "9"      # 只保留 bit0 与 bit3
```

## 3. 机器码后端（整个函数可翻译时）

如果函数体全部落在整数子集里，整个函数会被翻译成 x86-64 机器码，调用时直接执行原生代码：

* 允许的指令：局部变量读写、整数加减乘、六种比较、条件跳转、无条件跳转/回跳、返回；
* 整数运算直接在虚拟寄存器上完成（原生栈帧里），没有逐条指令的派发开销；
* **参数与未确定赋值的局部变量在调用前检查**：不是整数就照常解释执行，语义不变；
* 返回值的类型（`int` / `int64` / `bool`）用运行期种类字节记录，因此 `typeof` 与解释器一致；
* 每个"回跳目标且操作数栈为空"的循环头都有一个入口（trampoline：先做栈帧开场再跳到循环头），
  这就是自动提升能在一个函数执行到一半时接管的原因。

翻译不了的情况（字符串、列表、调用、闭包、创建闭包、容器操作、无法证明类型的运算……）会安静地
退回解释器，所以带不带标记都不会让程序出错。

## 4. 实测

同一台机器（MinGW-w64 g++ 13.1，`-O2`，单核）：

| 工作 | 未优化 | 机器码 |
| --- | --- | --- |
| `while` 循环 40 万次（不写标记，靠自动提升） | 69 ms（纯解释） | **约 1 ms** |
| `while` 循环 40 万次（写 `[[jit]]`） | — | **不到 1 ms** |
| 10 次加法循环体 30 万次 | 192 ms | **1 ms** |
| `annota bench` 的 `vm jit on loop` | 175 ns/迭代（关闭后端） | **1.2–1.5 ns/迭代** |

对照的 C++ 基准（`tools/cpp_baseline.cpp`）里，同一个循环是 0.21 ns/迭代，也就是说整数热循环已经
落在 C++ 的个位数倍以内，而不是几百倍。复现方式见 [tools.md](tools.md) §7。

### 时间花在哪：先量，再优化

整数循环之外，开销**不在派发条数**上。 同一台机器上量出来的两个数字：

| 场景 | 实测 | 说明 |
| --- | --- | --- |
| 2000 次调用 `f(n)`，函数体是 4000 次 `while` | 20 ms（**10 µs/次**） | 标量实参：调用 + 循环体 |
| 2000 次调用 `g(xs)`，`xs` 是 4000 元素列表 | 4477 ms（**2.24 ms/次**） | 容器实参按值语义**每次深拷贝** ≈560 ns/元素 |

也就是说：容器的深拷贝比函数真正的工作贵 **200 倍以上**，`examples/perf.ant` 里
`二分查找` / `哈希查找` 这类行看起来是 C++ 的几百倍，主要就是这个原因（C++ 传引用，不拷贝）。

已经按这个顺序做了第一步——**`lend` 参数**（见 [syntax.md](syntax.md) §4.1.3）：callee 声明
"此参数只读"，调用边界就不再复制；编译器强制这个承诺（改它、返回它、别名保存、闭包捕获、或
拿它当方法接收者都会**编译报错**）。标准库的排序/查找族已全部改用它，另外把
`seqnative.lower_bound` / `upper_bound` 从"每次调用物化整张表"改成在原地二分。效果
（同一台机器，`examples/perf.ant`）：

| 行 | 改前 | 改后 | C++ -O0 |
| --- | --- | --- | --- |
| 二分查找 (4000 元素) | 440 ms | **14 ms** | 0.49 ms |
| 堆排序 (脚本) | 21 ms | 21 ms | — |
| 动态列表 push | 63 ms | 52 ms | 1.65 ms |
| 筛法求素数 | 45 ms | 38 ms | 1.51 ms |
| Dijkstra (14x14 网格) | 63 ms | 49 ms | 0.18 ms |
| 编辑距离 (80x80) | 623 ms | 487 ms | 3.27 ms |
| 矩阵乘 (30x30) | 25 ms | 18 ms | 0.04 ms |
| 函数调用 (4 万次) | 23 ms | 21 ms | 0.07 ms |
| **合计** | **1.60 s** | **0.96 s** | **~16 ms** |

剩下的差距集中在两处，都是 JIT 的覆盖范围，而不是派发条数：
**数组访问进 JIT**（矩阵乘、编辑距离、筛法的内层循环）与**被编译函数之间的直接调用**
（`函数调用` 那一行，以及所有"一层薄封装套一层薄封装"的库路径）。

## 5. 什么时候该用哪条路线

| 情况 | 建议 |
| --- | --- |
| Annota 里的纯整数循环 | 什么都不用做（自动提升）；想提前编译就写 `[[jit]]` |
| 算法内核（排序、筛法、矩阵、字符串扫描……） | 链接 C++，见 [FFI](ffi.md) |
| 只是写法啰嗦、想复用 | 标准库脚本模块（`lib/*.mod`） |

## 5. 调用：解释器的直接调用与 JIT 的原生调用

调用曾经是解释器最贵的一步（构造参数表 + 压入 callee + 逐层绑定）。现在分两层：

* **解释器**：对程序里自己定义的顶层函数、以及 `[[static]]` 类方法，编译器发射
  `call_direct <名字> <实参个数>`——不构造参数表、不压 callee，VM 直接从操作数栈绑定实参
  （类限定调用会把该类作为 `this` 传入，方法体里的裸调用因此照旧解析）。名字可能被遮蔽
  （同名局部/上值、程序里任何赋值、所在类的同名方法）时仍走通用路径；运行期名字不再是函数时
  自动回退。
* **机器码**：被编译的调用者在满足"callee 已有机器码、实参静态确定是整数、实参个数一致、
  callee 不是方法、且结果种类静态唯一"时，直接发原生 `call`：实参从虚拟寄存器搬到 callee 的
  `L[]`（放在调用者的原生栈上，因此递归安全），结果从 `JitOut` 取回。解析 callee 时会按需编译
  它（用 busy 标志断开递归环）。

`examples/perf.ant` 的调用行因此从 23 ms 降到 **11 ms**。注意第二层目前只在"结果种类不依赖实参
种类"的 callee 上生效：`f(x) = x + 1` 这类函数的结果种类仍要解释器动态决定，这是下一步要解决的
（要么给 JIT 传实参种类字节并动态传播，要么按种类特化编译变体）。
